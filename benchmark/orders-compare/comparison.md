# Orders Q1..Q10 — kaidb vs MySQL vs PostgreSQL

Generated by the Kyte `orders-compare` harness (`benchmark/orders-compare`), 2026-09-16.

## Setup

- **Rows:** 1,000,000, generated by a seeded RNG so every engine loads byte-identical data.
- **Schema:** `orders(id PK, order_date, due_date, ship_date, employee_id, customer_id, sub_total, tax_amt, freight, total_due, details)`; secondary indexes on `employee_id`, `customer_id`, `total_due`, and a composite `(employee_id, total_due)`; indexes built after the load.
- **Timing:** each query run twice, the **warm** (second) pass reported; full client round-trip (server executes and all result rows are fetched back over the wire) through the Kyte driver packages.
- **Host:** MacBook Air (M1, 8 cores, 8 GB RAM), macOS 26.6.2.
- **Engines:** kaidb/NovaDB (Release build, auto buffer pool = 4096 MiB) on a **fresh, empty data dir** (port 3010); MySQL 9.7.1 (default config); PostgreSQL 18.x.
- **Data model:** money columns are stored as whole-number doubles, so the same generated data loads identically everywhere and the query set is byte-for-byte the same string per engine.

> **Why a fresh kaidb data dir.** kaidb's `DROP TABLE` does not reclaim a table's storage, and neither `DROP`+`CREATE` nor `DELETE FROM` clears the table's primary-key index (COUNT reads 0 while the PK index still holds the old keys). Re-running the benchmark against a dirty database therefore both fails to reload and drags query times down because the file and buffer pool are bloated with leftover tables. This run used a brand-new empty data dir, which is the only way to get a clean, comparable kaidb measurement today. See "Known kaidb issues" below.

## Reading of the results

- **MySQL wins the point and range queries (Q1..Q8) by roughly 1.6x–2.2x** and loads ~4.5x faster. These are index-seek + fetch-N-rows queries where MySQL's mature executor is ahead.
- **kaidb wins the aggregates**: Q9 `COUNT(*)` is answered index-only (sub-millisecond vs 5 ms) and Q10 `AVG ... GROUP BY` is ~4.3x faster (30 ms vs 128 ms) via the index-only group-by over the covering `(employee_id, total_due)` index.
- kaidb's closest gaps are Q3 and Q8 (the filtered `ORDER BY total_due DESC` and the two-sided range). These are where its planner still does more work than MySQL, but on a clean data dir they are ~55 ms, not the ~150–170 ms seen when the database file was polluted with leftover tables.
- **PostgreSQL could not be measured**: the local server is stuck in recovery mode (`the database system is in recovery mode`) and rejects every connection, so all writes and reads fail. Re-run once it is out of recovery and the PostgreSQL column fills in automatically (`ORDERS_ENGINES=kaidb,mysql,postgres`).

## Known kaidb issues surfaced by this run

1. **DROP does not reclaim storage.** `DROP TABLE t` reports success but leaves the table's B-tree in `nova.db`; a same-name `CREATE` resurrects the old rows.
2. **DROP/DELETE do not clear the primary-key index.** After either, `COUNT(*)` reads 0 but re-inserting the old ids fails with `error.KeyAlreadyExists`. The only reliably clean table is one whose name was never used — hence the fresh-name/fresh-data-dir approach here.

Both are genuine engine correctness bugs and are good candidates for the next kaidb fix.

## Reproduce

```sh
cd benchmark/orders-compare
kyte build && codesign -s - -f build/debug/bin/orders-compare   # macOS

# kaidb must run on a FRESH, empty data dir (see note above). For example:
#   mkdir -p /tmp/kaidb-bench/data && cd /tmp/kaidb-bench
#   echo '{"port":3010,"primary":true,"base_dir":"data"}' > db.json
#   /path/to/kaidb/zig-out/bin/novadb &

KAIDB_URL='admin:admin@127.0.0.1:3010?db=default&tls=false' \
ORDERS_ROWS=1000000 ORDERS_ENGINES=kaidb,mysql,postgres \
./build/debug/bin/orders-compare
```
